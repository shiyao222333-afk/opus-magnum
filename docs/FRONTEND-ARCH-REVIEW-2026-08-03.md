## 三、混乱根源：三层导航套壳（实测确认）

```

│
├─ 第 2 层：Dashy 4000（独立 SPA）
│   ├─ 顶栏导航：巨作 / 文档 2 项（Dashy 自己的）
│   └─ 主页分区：工具入口 4 卡 / 研究报告 / 行动清单
│       └─ target=workspace 卡片 → 再内嵌 ↓
```

## 四、五维度详解

### ① 技术栈健康度 14/20 ⭐⭐⭐
- ✅ 选型合理：NiceGUI（Python SPA）+ Dashy（成熟仪表盘）+ 极简自研（行动清单纯标准库，零依赖）
- ✅ 授权干净：Dashy MIT / NiceGUI MIT / 自研无三方依赖，无 AGPL/LGPL 包袱（符合五器"闭源可收费"战略）
- ❌ 双份 SERVICES 定义（launcher/services.py 与 supervisor/launcher.py）——同概念两处维护，改一个漏一个
- ❌ 全 Python 无类型标注，跨服务调用靠口头约定（api_spec.md 有规范但无强制校验）

### ② 架构设计模式 6/20 ⭐⭐（混乱主因）
- ❌ **壳层职责不清**：谁才是"入口"？巨作说是总指挥部，Dashy 说是聚合入口——两个都抢入口，用户被迫记两套导航
- ❌ **循环依赖**：Dashy → 巨作 / → Dashy（周看板卡片），架构上有环，虽实际只嵌一层但扩展必踩
- ❌ **app.py 上帝文件**：页面渲染 + 导航 + 业务逻辑 + iframe 注入混在一个文件，改一处要通读全文件
- ❌ 组件粒度：巨作无页面级模块化（对比熔知 pages/ 目录已是标准做法）

### ③ 工程化成熟度 12/20 ⭐⭐⭐
- ✅ 托盘启动器统一托管 8 服务 + 启前端口清理 + supervisor 自愈 + 过期锁清理（缺陷 A/B 根治后很稳）
- ✅ README 已按五器模板更新、CHANGELOG 规范、BUGLOG 案例库在建（bug-triage 落地）
- ❌ 无 CI/CD（单机项目可接受，但无自动语法/冒烟门槛）
- ❌ 测试薄弱：仅 action-flow validate.py + 少量契约测试，巨作页面无自动化渲染验证（本次显示墙 bug 就是"只验端口 200 没验渲染"漏的）

### ④ 性能与可维护性 8/20 ⭐⭐
- ❌ 三层 iframe 嵌套：Dashy workspace 内嵌再开 iframe，每层独立加载内存/网络
- ❌ 巨作 /wall 每次全量加载 Dashy SPA（无缓存/懒加载策略）
- ❌ 导航视觉三套（巨作深灰抽屉 / Dashy 深色卡片墙 / 熔知深灰抽屉），切换时心智负担重
- ❌ 改导航要动 3+ 个文件（app.py / conf.yml / 各服务 ui_shared）

### ⑤ 综合体验 10/20 ⭐⭐⭐
- ✅ 功能齐全：看板/摄入/显示墙/总指挥/行动清单全可用，6 服务稳定在线
- ❌ 用户真实体感"混乱"与代码结构一致：每点一层都要重新找"入口在哪"

## 五、重构优先级

| 优先级 | 动作 | 预期收益 | 估算 |
|:---:|---|---|---|
| **P0** | **定单一导航壳**：二选一 —— ①巨作做唯一壳（Dashy 顶栏导航清掉，Dashy 退化为纯内容墙，巨作左抽屉加"外部工具"分组：熔知/凝华/B站/行动清单）或 ②Dashy 做门户（巨作页面去左抽屉改极简，收进 Dashy 卡片） | 消除双壳并列，用户只认一套入口 | 2-3h |
| **P0** | **拆循环嵌套**：Dashy"周看板"卡片改新窗口（target=_blank）或改指巨作 /ingest，禁止 Dashy 内嵌巨作 `/` | 架构去环，杜绝套娃 | 0.5h |
| **P1** | **合并双份 SERVICES**：删 front_half/supervisor/launcher.py，app.py 统一 import launcher/services.py | 服务定义单一权威，改一处全生效 | 1h |
| **P1** | **巨作 app.py 拆页**：pages/dashboard.py、ingest.py、hq.py、wall.py + utils/ui_shared.py（左抽屉抽公共），对齐熔知结构 | 上帝文件拆解，每页独立可测 | 2-3h |
| **P1** | **统一导航代码**：巨作/熔知/凝华三份 build_left_drawer 合并为共享组件（或至少提取模板保持同步） | 导航改一处三处生效，视觉统一 | 2h |
| **P2** | Dashy 卡片 target 策略统一（每类工具定一种：内嵌 or 新窗口） | 交互可预期 | 1h |
| **P2** | 行动清单 / B站 加统一顶部条 | 视觉一致性 | 1h |
| **P2** | 巨作 /wall iframe 缓存/懒加载优化 | 减少每次全量加载 | 1-2h |

## 六、建议路线（先想清楚再动手）

1. **先定 P0 的壳策略**（你拍板：巨作做壳，还是 Dashy 做门户）——这是根，定了才动 P1/P2
2. P0 两件事做完 → 用户体感立刻从"混乱"变"只有一个入口"
3. P1 结构债是"趁热打铁"，拆完 app.py 后每个页面独立维护、独立验证（能防再次出现"端口通但页面坏"）
4. P2 是锦上添花，可排后

> 架构没有银弹，合适的才是最好的。当前"双壳"在功能上没坏，但每加一个新工具就要决定"放巨作还是放 Dashy"，这个决策成本会随工具数线性增长——这就是现在就该收编的原因。
