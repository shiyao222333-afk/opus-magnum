## 0. 背景：我们要解决什么

- **现状**：炼真（Albedo）对单条视频/文档抽取"主张(claims)"，你反馈"抽取的主张本身没有意义"——它们是视频内的自述性内容，离开上下文没有认知价值。
- **根因（AI 设计诊断，非用户指令）**：验真轴把两件事混为一谈——
  - "可被核查"（check_worthy）
  - "值得知道"（worth_knowing，有认知负载）
  
  系统其实已有"有意义抽取"路径（`core/merit.py`：核心洞见 / 可复用步骤 / 差异点 / 坑 / 适用场景 / 迁移成本），但验真轴没消费它。
- **已落地（A 方案）**：Layer2（字幕作语料）降级为"忠实度门(faithfulness)"，不再写 `accuracy` 抬高 `trust_score`（避免 x=x 循环论证）。
- **已确认（C 方案）**：跨源矛盾检测本就是熔知的设计意图，不变。
- **真正解法**：B 不是改抽取提示词，而是让"主张"在**多源碰撞**中显现价值——这正是炼真+熔知联合闭环要做的事（见 §1）。

## 1. 两项目联合验真闭环（对你四点评述的映射）

你的四点评述 → 系统落点：

| 你的评述 | 系统落点 |
|---------|---------|
| 1. 知识库空→未来内容多，炼真联动熔知 | 熔知做跨源矛盾/支持检测（C），炼真把命中结果反写报告 |
| 2. 摄入熔知的文件无数据支撑→天然进待审核队列→人工补录支持数据到熔知库→文件重新过炼真 | 需熔知"文档下载" + "送回炼真监控文件夹"两个接口（未来开发项） |
| 3. 研究开源情报(OSINT)技术 | 已有成熟工具（见 §2） |
| 4. 验真环节暂无支持是正常的 | 未来开发，不阻塞当前 |

**闭环（文字版，你看不到图）：**
```
视频/文档
   │  炼真抽取主张
   ▼
 主张 claims
   │
   ├──────────────────────┬─────────────────────────┐
   ▼                      ▼                          ▼
熔知跨源矛盾/支持检测(C)   无数据 → needs_review 队列    人工补录 OR OSINT agent
   │                      │                          │
```

## 2. 开源情报 / 事实核查工具调研

混合事实核查范式 = **知识图谱 + LLM + 检索智能体（Search Retrieval Agent）**。技术底座已成熟，未来验真环节不必从零造：

| 工具 | 类型 | 用途 | 可用性 |
|------|------|------|--------|
| **Wikidata** | 知识库 | 3 亿+ 实体，结构化事实源 | 公开 API |
| **ProVe** | 验证器 | 基于 Wikidata 的事实验证，带 Web API | 开源 |
| **FEVER** | 数据集 | 185K 声明·事实核查基准 | 公开 |
| **FactNet** | 图谱 | 1.7B 跨语言 事实↔证据 图 | 研究 |
| **aiFactCheck** | 流水线 | 模块化开源事实核查管线 | 开源 |

**结论**：优先接入 Wikidata / ProVe 类**结构化事实源**，比让 LLM 自由联网检索更稳、可溯源。

## 3. 多信源互证（深研）

核心问题：多个来源说同一件事，怎么判断"真"？

### 3.1 多源知识融合（multi-source knowledge fusion）
- 三大子问题：**冲突检测**(conflict detection) + **实体对齐**(entity alignment) + **真相发现**(truth discovery)。
- 数据融合本质 = "辨识数据真实性 + 源可靠性 + 解决数值冲突"。

### 3.2 来源可靠性迭代推断（Nari 框架，国防科大综述）
两条相互印证的规则：
- "可靠来源提供的知识更可信"
- "提供可信知识，反过来反映来源的可靠性"

做法：先假设来源可靠性 → 推断事实真伪 → 再用推断出的事实真伪，反过来更新来源可靠性。**迭代收敛**。
→ 对熔知的启示：`trust_score` 和来源可信度要**联合学习**，不能单方面拍。

### 3.3 多源线图 + 多级置信（MultiRAG，BAAI 开源）
- 把多个来源建成"线图(line graph)"，聚合逻辑关系。
- 两级置信：**图级(graph-level)** + **节点级(node-level)**，过滤不可靠节点。
→ 对熔知的启示：置信不是单一标量，应**分层**（来源层 / 事实层 / 跨源层）。

### 3.4 信源互指网络（cross-platform citation）
- 跨平台互相引用 → 置信度**指数级**提升。
- 建模为"引用"边，权重高于单源。
→ 对熔知的启示：记录"谁引用了谁"，互指越多越可信。

### 3.5 投票机制（冲突消解）
- 多个**独立可靠源**支持同一事实 → 采纳。
- 显式记录冲突，标注"待验证"。
- 时效性优先（新数据覆盖旧数据，视领域而定）。

### 3.6 落地到熔知的可信度分层（AI 设计提案，待确认）
```
Layer-A  来源可信度（静态）：按 §4 五级评定
Layer-B  事实置信（动态）：本篇内多源是否一致
Layer-C  跨源互证（联动）：与熔知库其他文档矛盾/支持
最终 trust_score = f(A, B, C)，权重待标定
```

## 4. 信源可信度分级 —— 单轴五级（用户采用模型）

> **用户拍板**：不用北约双轴（太复杂），改用**单轴五级**——按"离原始 / 客观多远"排序，**数字越大越不可信**。
> 你给的 ① ② ⑤ 档：① 原始数据或论文　② 聚合这些信息的平台　⑤ 主观观点。③ ④ 你忘了，下表为常见补位（**待你确认**）。

| 级 | 类型 | 含义 / 例子 | 可信度 |
|----|------|------------|--------|
| 1 | 原始数据 / 论文 | 一手观测、实验数据、同行评审论文 | 最高（事实基准） |
| 2 | 聚合平台 | 把多篇原始信息聚起来、可检索的库（Wikidata、权威数据库、维基、行业库） | 高（已结构化 / 策展） |
| 3 | 新闻媒体 | 正规媒体报道、转述（官媒 / 市场化媒体 / 行业媒体） | 中（编辑过，需交叉核） |
| 4 | 自媒体 / 社交平台 | 个人账号、公众号、论坛、短视频（UGC） | 低（仅作线索） |
| 5 | 主观观点 / 传言 | 个人看法、匿名爆料、无出处的猜测 | 极低（默认干扰项） |

**对熔知的意义**：每条入库事实打一个 **`source_tier`(1–5)** 标签即可（比双轴简单）。跨源互证时：高 tier（1–2）权重高、可单独采信；低 tier（4–5）只作线索、不单独采信。这也正好对应多信源互证里的"信源互指网络 / 投票机制"——多条独立高 tier 源互指 → 置信跳升。

> ⚠️ 当前炼真契约字段只有 `trust_score(0–5)`（2026-07-25 你裁定，不增殖）。`source_tier` 是**未来增强方向**，需你拍板是否引入，不擅自加字段。
> 备选参考（**未采用**）：北约 6×6 双轴系统（信源可靠性 A–E + 信息可信度 1–5），更细但你认为太复杂。

## 5. 熔知版本升级需求（设计记录，已读代码）

- **需求**：未来熔知要支持**已入库文件的版本升级**——同一文档出新版本时，重新摄入并**追踪历史**（不丢旧版本，可比对差异）。
- **当前状态（2026-07-29 读 `doc_manager.py` 确认）**：熔知目前是**覆盖更新**——重摄入时 upsert 新块并删除旧版本孤儿块（`delete_orphan_points`, `doc_manager.py:670-690`）。**没有版本历史**，旧版证据会被覆盖。
- **与联合闭环的关系**：版本升级是"回送炼真重新验真"的前提——人工补录 / OSINT 更新后，文件以**新版本**回流，旧版证据保留可追溯。
- **待办**：设计版本表（doc_id + version + parent_version + diff），重摄入时写新版本而非覆盖。
