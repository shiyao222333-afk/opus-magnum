## 1. 现象
- 20 条提交（01:28）→ 过一晚收藏夹仍 13 条未删，用户质疑"太久了吧"

## 2. 调试历程（证据链）
### 阶段一：怀疑管线断（第 1 轮）❌
- 假设：炼真/熔知消费端挂了导致卡住
- 验证：炼真 watcher 无锁文件、熔知 server.log 有 bind 失败 → 看似"断了"
- 实际：**那些是重启前的旧痕迹；Qdrant 点数持续上涨=管线实际在跑**
- 结论：❌ 排除 — 管线没断，是"慢+异常重置"的错觉

### 阶段二：白干重跑（第 2 轮）✅
- 假设：recover_stale() 把已完成但未出队的 processing 项重置回 pending → 重新下载+ASR
- 验证：done/ 8 条 vs 队列 5 条被重置 → **5 条 100% 重叠**；全量扫熔知 60 个 BV → **5 条全部已入库**
- 根因链：dm.process() 写完中转①（done 归档=炼真处理过）→ **complete() 出队前消费进程崩溃** → 重启后 recover_stale() 见 processing 且 pid 死 → 重置 pending → **重新下载+ASR+精炼白干一遍**
- 结论：✅ 确认 — 5 条白干重跑是"慢"的主因之一（每条重跑浪费数十分钟）

### 阶段三：用户重启电脑（第 3 轮）✅
- 用户澄清"离线是因为我重启了电脑"→ Qdrant/熔知离线=服务未自启，**不是 bug**
- 重启前管线其实一直在跑（07:44/45 还有 done 产出、点数持续涨）

## 5. 遗留教训（下次注意）
- **诊断"管线慢"先看"已完成 vs 队列状态"重叠**——done 归档 ≠ 队列出队，二者不同步说明有崩溃残留
- recover_stale() 的语义是"回收崩溃残留"，但它**无法区分"处理中"和"已完成未出队"**——这是设计盲区，将来可在 process() 返回成功时立即 complete() 缩小窗口
- 用户重启电脑 → 服务不自启，靠总管 start_all 拉起即可，Qdrant/熔知数据无损

## 6. 追加：崩溃终极根因 + 修复（09:56）

### 根因升级（08-05 实锤）
- 此前怀疑"管线断/ASR 卡死"都是表象；**08:52:32 消费者真实死因 = 队列锁残留 → 抢锁超时 → 异常链崩溃**：
  1. complete() 释放锁时 `_force_delete`（cmd del）被拦 → 锁文件删不掉
  2. 下一条 complete() 抢锁等 10s 超时 → 抛"队列锁获取超时"
  3. main 的 except 兜底调 fail() → fail() 也抢锁失败 → **二次抛错冒顶 → 进程崩溃**
- **钩子真实拦截原因（沙箱诊断输出）**：`windows-sandbox-recycle-bin-unavailable`（沙箱回收站不可用 → fail-closed 拒绝删除）；对相对路径还报 `relative path rejected`。**08-04 写的 cmd del 绕法已失效**（钩子影响面扩大，连 cmd del 也拦）

### 修复（用户确认后落地，queue.py `_force_delete`）
- **删除优先 + 改名兜底 + 顺手清残留**（纯 Python 内置，零外部依赖，不新增硬编码路径）：
  1. `os.remove(path)` 优先（生产进程沙箱外可直接删，零残留）
  2. 被拦则 `os.replace(path, path+".del")` 改名腾位（钩子拦"删除"不拦"改名"，O_EXCL 新锁可建）
  3. `_acquire_lock` 成功时 `_cleanup_del_residue()` 清历史 .del（不堆积）
- 验证：语法 + 4 场景全过（删除优先/改名兜底模拟 os.remove 拦截/残留清理/抢锁自动清）；测试中钩子真实触发（沙箱内 os.remove 被拦 → 改名兜底自动接管不崩）✅
- 消费者已重启加载新代码（pid 9112，心跳正常，队列 0）
