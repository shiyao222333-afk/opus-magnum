# 项目反哺调研规范（RESEARCH-GUIDE）v3.5 — 双账本 + 固定5条 + 项目提升 + 白话分析版

> 用途：项目反哺调研的深度调研 + **任务拆解**执行标准。自动化任务（每周一 9:00）与对话手动触发共用同一套流程。
> **输入**：`python scan.py --json` 的 **new + changed**（= 行动清单记账本无状态的未调研条目），**每次固定取前 5 条**。

> - 审核清单账本 `pending/state.json`：管"审核到哪一步"（pending/approved/rejected）——**审核清单有自己的账本**
> - 审核结论必须**反哺**行动清单记账本（批准=保持 need_deep 进执行；打回=archived 防重复调研）
> v3.5 核心：①决策规则卡（记忆提炼，标来源）②7 步调研带 decision_rules/validation/escalation ③借鉴点四件套 ④共性提炼 ⑤固定 5 条制 ⑥双账本反哺 ⑦Gate：只产清单绝不执行 ⑧**💡 项目提升**（做完后可感知画面，禁空话）⑨**已有/差距白话四要素**（通俗易懂，禁止术语堆砌）⑩**多 doc_id 支持**（一个行动条目可对应多个来源）。
> 项目归属：按 `projects.json`（10 项目：巨作/行动清单/审核清单/B站仪表盘/熔知/凝华/馏析/炼真/鲜管家/视频制作），匹配不到不归类。

## 调研步骤（对每条条目，7 步全走，一步不能跳过）

### 0️⃣ Pre-flight（先加载记忆与输入）
- 读本文件「决策规则卡」（上方 A/B/C 三区）
- 读 `docs/feedback-log.md`（纠正日志——上次用户纠正过什么，这次不重犯）
- 读审核清单账本 `pending/state.json` + `pending/items/`（了解已调研/已审批，避免重复）
- 跑 `python scan.py --json` → 取 **new + changed** 前 5 条作为本轮候选；0 条 → 报告"本轮无新条目"结束

### 1️⃣ 读条目
- **decision_rules**：取 标题、依据、doc_id、所属项目（按 projects.json 关键词判断）；分类（新功能建议 / 架构对照 / 方法论迁移 / 产品形态分析）
- **validation**：四要素齐全（标题/依据/doc_id/项目）才继续，缺 doc_id 直接标"无法调研"并跳过
- **escalation**：条目含义模糊 → 停在条目层，报告"该条无法理解"，不硬编

### 2️⃣ 读熔知文档内容（条目到底说了什么）
- **decision_rules**：用 doc_id 查 Qdrant（scroll filter doc_id），读 title / auto_summary / 关键正文段落。**禁止只看标题就下判断**（用户红线：diff 真实内容）
- **validation**：记录文档实际内容要点（1-2 句），写进笔记「🔎 原文要点」
- **escalation**：查不到该 doc_id → 报告"知识库中不存在"，不编造内容

### 3️⃣ 进网页看原文（如有，必做）
- **decision_rules**：取 `origin.source_url`；文章/博客 → WebFetch；B站视频（反爬）→ **WebSearch 搜同主题网页文章**（文章名/核心概念+项目名）；只有确实查不到才以熔知内容为准并在笔记注明
- **validation**：网页要点（1-2 句）写进笔记「🌐 网页查证」；注明"以熔知内容为准"的情况
- **escalation**：网页打不开/搜不到 → 注明后继续（不以熔知为准以外的方式猜测）

### 4️⃣ 深挖项目代码（这条能不能用、怎么用）——已有/差距白话四要素 + 借鉴点四件套
- **decision_rules**：打开对应项目 README / 关键代码 / 已有功能，**具体到文件**。判断：
  1. **已有**（现在有什么，白话详细版）：
     - ① 它是什么：**白话一句话**说明现状功能是干嘛的（不许甩术语）
     - ② 打个比方：用生活化类比说它现在怎么工作
     - ③ 结论：这步我们已经有了，不用做 / 只覆盖了部分
  2. **差距**（缺什么，白话详细版）：
     - ① 缺什么：白话一句话
     - ② 缺了它现在会怎样：现在的局限/痛点（具体场景）
     - ③ 补上后你能…：可感知的画面
  3. 若能落地，动哪些文件（列路径）
  4. **借鉴点四件套**：可借鉴点 | 难度🟢🟡🔴 | 对项目价值 | 最佳切入点
  5. **护城河检查**：学了会不会丢差异化？
- **validation**：代码分析结论写进笔记「💻 代码分析」（**已有 + 差距 分开写，白话版**）；必须有具体文件，不能只写"看看"
- **escalation**：找不到对应代码 → 报告"项目无对应实现"，基于 README 判断

### 4.5️⃣ 项目提升（做完后用户实际能体验到什么）——v3.5 新增
- **decision_rules**：用一句话或几句话描述**做完这些任务后，用户能做什么以前做不到的事 / 项目体验有什么变化**。必须是**可感知的画面**（对标竞品报告"对 Athanor 的价值"列写法："搜 Transformer 时自动发现相关论文、作者、机构"）
- **validation**：写进笔记「💡 项目提升」；检查是否含空话（提升效率/增强能力/更好体验 → 打回重写，必须具体到"你能…"）
- **escalation**：想不出具体画面 → 说明这条价值未想清楚，标注"价值待确认"

### 5️⃣ 风险评估 + 拆解任务清单
- **decision_rules**：风险三档：
  - 🟢 低：新增/独立改动，不影响现有功能
  - 🟡 中：改动现有模块，需回归
  - 🔴 高：动核心链路/数据契约，需谨慎论证
  拆任务：3~8 条，每条含「做什么（动词开头）/ 涉及文件（具体路径或"新建"）/ 验收标准（可观测）」，有依赖标顺序（①→②→③）
- **validation**：任务拆解写进笔记「📋 任务拆解」；**拆不出任务 = 没价值**（标 archived）
- **escalation**：风险🔴高 → 标「暂缓」并注明原因，不硬推

### 6️⃣ 共性提炼（跨条目找共性，**只提示不合并**）
- **decision_rules**：本轮全部条目调研完后回看——≥2 条独立来源指向同一方向（如同为 skill 封装、同为知识图谱）→ **只做提示，绝不合并**：报告里列出「🔺多源印证：A/B/C 同指向 X 方向」，但**每条 doc_id 各自独立拆任务、独立呈现、独立审批**（用户 2026-08-04 拍板：多个条目不应该对应一个项目，禁止合并成一条行动）
- **validation**：报告里列出"本批共性发现"（如有）；每条 doc_id 单独标账本（need_deep+pending 逐条）
- **escalation**：无

### 7️⃣ 落盘调研笔记 + 批量反哺记账本（Gate：只产清单，绝不执行）
- **decision_rules**：
  1. 每条调研结果写调研笔记 `pending/items/{doc_id}.md`（纯内容：原文要点/网页查证/代码分析（已有+差距白话版）/项目提升/风险/任务拆解，**不含状态**）。**每条 doc_id 独立成笔记、独立任务拆解，禁止"并入主条目"写法**
  2. 收齐后**统一批量反哺**（子任务不写记账本，防并发写坏）：
     - 有价值 → 对**每个 doc_id** 执行 `python mark_status.py <doc_id> need_deep`（行动清单）+ `python mark_pending.py <doc_id> pending`（审核清单）
     - 没价值/已覆盖/拆不出任务 → `python mark_status.py <doc_id> archived`（行动清单：归档，**不进审核清单**）
- **validation**：输出前自审（[自审]）：
  - 每条结论有依据吗（读了原文/查了网页/看了代码）？
  - 「已有/差距」是白话吗？有打比方吗？说清"缺了会怎样、有了会怎样"了吗？（术语堆砌 → 不过）
  - 「💡 项目提升」是可感知画面吗？含空话 → 不过
  - 借鉴点四件套齐全吗？
  - 任务拆解 3~8 条、每条有文件+验收吗？
  - 有没有把 AI 自创规则当用户指令？（红线）
  - 有没有误合并多源条目？（多条知识必须各自独立，禁止并成一个项目条目）
  - 双账本动作写对了吗（有价值=need_deep+pending 逐 doc_id；没价值=archived）？
- **escalation**：Qdrant 离线 → 报告"跳过本轮，Qdrant 离线"，不强行执行；任何一步卡住 → 停下报告，不硬编
- **Gate**：产出调研笔记 + 标账本 = 终点。**绝不自动执行任何行动**；等你批准

## 价值判定

| 判定 | 条件 | 动作（双账本） |
|---|---|---|
| ✅ **有价值** | 与项目方向相关 + 可落地（对照后能实施）+ 风险可接受 + 能拆出 3~8 条任务 | 行动清单 `need_deep` + 审核清单 `pending`（**逐 doc_id**）+ 调研笔记落盘 |
| ❌ **没价值** | 与项目无关 / 已被现有功能覆盖 / 技术栈不匹配 / 风险过大 / 拆不出任务 | 行动清单 `archived`（不进审核清单） |
| ⏸️ **暂缓** | 方向相关但时机不成熟 / 依赖未就绪 / 黑盒不可控 | 行动清单 `need_deep` 也可，但笔记注明"暂缓原因" |

**去重**：候选来自 scan.py（记账本无状态 = 未调研），天然排除已归档/已完成/已深入——**核对去重全部由记账本完成**。

```
# {来源文档标题}
- 项目：{项目名} | 方向：{方向} | 来源：{来源} | 依据：{一句话理由} | 优先：{高/中/低} | doc_id：{id}
  （一条知识可对应多个项目时：项目：{项目A}、{项目B}——多值，逗号分隔；禁止多条 doc_id 合并成一条行动）
  🔎 原文要点：{第2步结论，1-2句}
  🌐 网页查证：{第3步结论，1-2句，注明"以熔知内容为准"的情况}
  💻 代码分析：
     已有：①它是什么（白话一句话）②打比方 ③结论（这步不用做/只覆盖部分）
     差距：①缺什么（白话）②缺了现在会怎样（痛点）③补上后你能…（画面）
     涉及文件：{路径列表}
  💡 项目提升：做完后，你能…（可感知画面，禁空话）
  ⚠️ 风险：{🟢低/🟡中/🔴高}：{一句话说明}
  📋 任务拆解：
    ① {做什么} → 文件：{路径} → 验收：{标准}
    ② ...（3~8 条，含依赖顺序）
```

### 记账本动作（批量，收齐后统一执行；多 doc_id 逐条执行）

- 有价值 → 对每个 doc_id：`python mark_status.py <doc_id> need_deep` + `python mark_pending.py <doc_id> pending`
- 没价值 → `python mark_status.py <doc_id> archived`

### 审核清单条目（`pending/state.json` 渲染 + 移入 weekly 时）

- 每条 doc_id 独立成条目、独立审批（用户 2026-08-04 拍板：**多条知识不得对应一个项目**，禁止合并）
- 一个条目可对应**多个项目**：项目字段多值（`项目：熔知、巨作`，逗号分隔）——同一知识可被多个项目借鉴

### 调研报告（对话/任务输出）

按项目分组汇报：调研了哪几条、各判定结果、风险档、进审核清单几条、归档几条、**共性发现（多源合并）**。每条给出**💡 项目提升**（可感知画面）+ 任务拆解摘要（3~5 条）。**重要结论必须在对话里说人话总结**（用户无法查看 md 文件），「已有/差距」用白话讲。

## 审批流程（对话操作，用户说「批准 X / 打回 X」）

- **批准** → 对**每个 doc_id** 执行 `python mark_pending.py <doc_id> approved`（审核清单标已批准）+ 把条目（含任务拆解、💡 项目提升，取自 `pending/items/{doc_id}.md`）追加进 `weekly/` 最新清单对应项目小节（多 doc_id 合并为一条行动）。行动清单保持 need_deep（= 进入执行，完成再标 done）
- **打回** → 对**每个 doc_id** 执行 `python mark_pending.py <doc_id> rejected`（审核清单标已打回 + **反哺行动清单 archived**）+ 理由记入 `docs/feedback-log.md`
- 审核动作后审核清单账本状态变化 → /pending 页面条目自动消失（页面从账本实时渲染）

**别和审核清单搞混**：审核清单管"知识→行动"（自动化调研产出），技能封装清单管"知识→技能"（**用户指定才进**）。

- 清单文件：`skills_candidates.json`（个人数据，不上传 git；`skill_candidates.py` 是工具，上传）
- 状态机：`pending`（待封装）→ `doing`（封装中）→ `done`（已完成）；`pending` → `abandoned`（放弃，**必须带理由**，防下次重复评估）
- 入口只有一条：**用户指定**（如「把这条加进技能封装清单」「封装清单第 X 条」）→ `python skill_candidates.py add "<标题>" [doc_id]`
- **自动化调研不自动进技能清单、不标可封装度**（用户 2026-08-04 拍板"先不要，只要主路线"）；调研时若发现某条方法论密度高，可在对话报告里**口头提示**用户"可考虑加入技能封装清单"，决定权在用户
- 封装执行：**按仓颉插件执行（直接引用，不复制）**——读 `wall/action-flow/plugins/cangjie-skill/SKILL.md`（RIA-TV++ 七阶段：Adler 分析→5 提取器→三重验证→RIA++ 构造→Zettelkasten 链接→压力测试→交付）+ 需要时读 `methodology/` 方法论文档；接线细节见 `docs/CANGJIE-INTEGRATION.md`；**单条知识→单技能时裁剪整书级产物**（BOOK_OVERVIEW/INDEX/DIGEST/GLOSSARY 不要），保留核心：三重验证→RIA++ 六段→压力测试（诱饵+跨 skill 混淆）→交付；产出 `SKILL.md` + `test-prompts.json` 落盘 `~/.workbuddy/skills/<name>/` → 真实测试 → 回写 `status done`（或 `abandoned "<理由>"`）。仓颉更新：`git pull`（/skills 页「更新仓颉」按钮或对话说「更新仓颉插件」）

## 🧰 配套：技能资产清单（2026-08-04 新建）

**和技能封装清单的区别**：封装清单 = 哪些知识"打算"变成技能（候选池，用户指定才进）；资产清单 = "已经"有哪些技能、什么状态（资产台账，持续维护）。闭环：封装完成 → 候选池标 done → 顺手 `add` 进资产清单。

- 清单文件：`skills_catalog.json`（个人数据，不上传 git；`skill_assets.py` 是工具，上传）
- 状态机：`active`（在用）↔ `idle`（闲置，待定去留）；`active/idle` → `retired`（淘汰，**必须带理由**）；`use` 自动把 idle 回春为 active
- 字段：name / desc / type（self 自建 / external 外部引入）/ source / status / last_used_at / created_at
- 用法：`python skill_assets.py add "<名称>" "<简介>" [--type self|external] [--source "来源"]` / `list`（按状态分组）/ `use <key>`（记录使用）/ `status <key> idle|retired "<理由>"`
- 谁维护：**用户指定 + 对话里的我顺手维护**——新增技能、用了一次（`use`）、淘汰（`retired` 带理由）都记；自动化调研不碰这张清单
- 与 SkillOS 方法论的关系：这张清单就是 SkillOS"三操作（增/改/删）+ 定期体检"的人工落地载体（2026-08-04 用户拍板：Skills生态条 → 建第四张清单）
