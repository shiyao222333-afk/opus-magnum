# 行动清单 & 审核清单 执行规范（v4.0）

> **本文件是两份清单的全部工作流**。自动化任务不内嵌步骤——任务 prompt 只写"调什么工具 + 一句话目标"，跑前**读本文件对应章节**按流程执行。对话手动触发同理。
>
> **自动化任务一览**（2026-08-05 用户拍板）：
> - 1/3/5 5:00 执行行动清单 → 按「第一章」
> - 每天 6:00 执行审核清单·第1批 → 按「第二章」第 1 批（调研取前 5 条候选 + 呈现待审前 5 条）
> - 每天 7:00 执行审核清单·第2批 → 按「第二章」第 2 批（调研再取 5 条=一天 10 条 + 呈现待审第 6~10 条）
> - 1/3/5 3:00 / 4:00 B站收藏夹摄入与核对删除 → 脚本 `front_half/bili_fav_sync.py`（submit / auto），自包含
>
> **双账本架构（用户 2026-08-04 拍板）**：
> - 行动清单记账本 `state.json`：管"值不值得做"（无状态 / need_deep / archived / done）
> - 审核清单账本 `pending/state.json`：管"审核到哪一步"（pending / approved / rejected）——**审核清单有自己的账本**
> - 审核结论必须**反哺**行动清单记账本（批准=保持 need_deep 进执行；打回=archived 防重复调研）
> - **调研判"没价值" ≠ 用户"打回"**：没价值=调研判的，直接归档不进审核清单；打回=用户审的，留 rejected 痕迹+理由记 feedback-log
>
> 项目归属：按 `projects.json`（12 项目：巨作/行动清单/审核清单/技能封装清单/技能资产清单/B站仪表盘/熔知/凝华/馏析/炼真/鲜管家/视频制作），一条知识可对应多个项目（多值），匹配不到不归类。

### B. 判断准则（分析类任务通用；AI 设计决策，待确认）

- **先盘点项目已有能力**（原生能力盘点）：借鉴外部方案前先看自家有没有现成机制；"有现成机制却建议自建" = 无效建议
- **护城河检查**：学了别人的会不会丢掉自家差异化？——"别人有 ≠ 该做"

# 第一章 执行行动清单（1/3/5 5:00 + 对话手动）

> 目标：**把新入库的知识提炼成行动条目，写进行动清单（weekly md），让清单内容更新**——这就是"执行行动清单"。产出（need_deep 条目）是第二章审核清单调研的输入（用户 2026-08-05 拍板：5 点行动清单输出 → 6/7 点审核清单输入）。
>
> **执行方法全部内置在行动清单自己的文件里，读文件照做即可，不要自己另写格式**：
> - 格式规范 → 读 `template.md`（四色标记/来源/依据/创建周/优先/🔥市场验证/doc_id/项目反哺归属规则，全部写死在那里）
> - 输入数据 → 跑 `scan.py --json`（new + changed = 新入库未提炼条目，含 doc_id）
> - 写入目标 → 最新的 `weekly/*.md`（保持现有分区结构，追加到对应分区）
> - 项目归属 → 读 `projects.json`（12 项目 keywords，匹配不到不归类）
> - 标记已提炼 → `mark_status.py <doc_id> need_deep`（防下次重复提炼）

## 步骤

0. **weekly 对齐记账本（源头清除，根因修复 2026-08-05）**：读记账本 `state.json` → archived 与 done 条目若在 weekly 里还挂着，**先从 weekly 移除**（归档=否决不做、已完成=做完了，都不再是"活"条目；weekly 只留未完成的待办，渲染层不需要任何特殊处理）
1. 读内置规范：`template.md`（条目格式+四色+归属规则，照此提炼）
2. 读最新行动清单：`weekly/` 下最新的 .md（记住现有分区结构与格式）
3. 跑：`cd /d/opus-magnum/wall/action-flow && python scan.py --json` → 取 **new + changed**（未提炼的新入库条目）
4. 逐条按 template.md 格式提炼成行动条目（标题/来源/依据/创建周/优先/doc_id），按**分区定位三步法**写入 weekly：
   ① 属项目（projects.json 12 项目 keywords 匹配）→「项目反哺·对应项目小节」
   ② 不属项目但属行动方向（变现试水/日常干活/路线导航）→ **追加进已有的顶层对应分区，禁止新建同名分区**
   ③ 都不匹配 → 不归类（晨报里注明跳过）
5. **追加写入 weekly 对应分区**（清单内容真实更新）
6. 记账本标 `need_deep`（逐条：`python mark_status.py <doc_id> need_deep`，防重复提炼）
7. **待办跟进（催办区，2026-08-05 新增）**：读记账本 `state.json` 的 need_deep 条目，按 `status_at` 距今天数检查积压：
   - 无调研笔记 且 >7 天 → 「⚠️ 已提炼未调研（超 1 周）」——该去调研了
   - 有调研笔记（= 审核清单 pending）且 >7 天 → 「⚠️ 待你审批（超 1 周）」
   - 任一 >21 天 → 标 🔺 加急
   → 更新 weekly「二、待办跟进」区（格式照 template.md：`- [ ] ⚠️ **标题**（已提醒第 N 周 | 类型） | 来源：{来源} | doc_id：{id}`，N=ceil(超期天数/7)）
   → 无超期 → 该区保持"（暂无待办）"
8. 输出晨报（对话，说人话）：新增提炼 N 条（列标题+所属项目）/ 无可提炼则报告"本轮无新条目" + 待办跟进 N 条（如有）

## Gate

- 提炼+写清单 = 终点；**深度调研归第二章**，本章不做调研
- 不删改已有条目（归档由清单页按钮/审批流程管理）

## 停止条件

- Qdrant 离线 → 报告"跳过本轮，Qdrant 离线"，不强行执行
- scan.py 报错 → 报告错误原因后结束

> 目标：①**项目反哺调研**（新知识深度调研 → 有价值的进审核清单）②**审核清单呈现**（待审条目分批给用户看）。**项目反哺调研已并入本流程**（2026-08-05 用户拍板）。
>
> 批次分工：6:00 第1批 = 调研取**前 5 条候选**（need_deep 无笔记）+ 呈现待审**前 5 条**；7:00 第2批 = 调研**再取 5 条候选**（6:00 已调研的条目有了笔记 → 不再出现，天然是新 5 条，一天共调研 10 条）+ 呈现待审**第 6~10 条**。

## 第 1 部分：项目反哺调研（每批取前 5 条候选，逐条 7 步全走，一步不跳）

### 0️⃣ Pre-flight
- 读本文件「决策规则卡」（上方 A/B/C 三区）
- 读 `docs/feedback-log.md`（纠正日志——上次用户纠正过什么，这次不重犯）
- 读审核清单账本 `pending/state.json` + `pending/items/`（了解已调研/已审批，避免重复）
- **调研候选（v4.1 修正，2026-08-05）**：读行动清单记账本 `state.json` → 取 `status==need_deep` 且 `pending/items/{doc_id}.md` **不存在的条目**（= 第一章已提炼、尚未调研），按 `status_at` 升序取前 5 条；0 条 → 本批报告"无待调研条目"结束
  （第一章已把新条目标 need_deep → scan 的 new=0，**不能再从 scan 取候选**；"无笔记"天然区分已调研/待调研：6:00 调研完的 5 条有了笔记 → 7:00 自动取到新 5 条）

### 1️⃣ 读条目
- 取 标题、依据、doc_id、所属项目（按 projects.json 12 项目 keywords 判断；一条知识可对应多项目写多值；匹配不到不归类）；缺 doc_id 标"无法调研"跳过
- 条目含义模糊 → 停在该条，报告"该条无法理解"，不硬编

### 2️⃣ 读原文（禁止只看标题）
- doc_id 查 Qdrant（scroll filter doc_id），读 title / auto_summary / 关键正文；记录「🔎 原文要点」
- 查不到 doc_id → 报告"知识库中不存在"，不编造

### 3️⃣ 进网页看原文
- 取 `origin.source_url`：文章/博客 → WebFetch；B站视频（反爬）→ **WebSearch 搜同主题网页文章**；只有确实查不到才以熔知内容为准并注明
- 记录「🌐 网页查证」

### 4️⃣ 深挖项目代码（已有/差距白话四要素 + 借鉴点四件套）
- **已有**（白话详细版）：①它是什么（白话一句话，不许甩术语）②打个比方 ③结论（这步不用做/只覆盖部分）
- **差距**（白话详细版）：①缺什么（白话）②缺了现在会怎样（具体痛点）③补上后你能…（可感知画面）
- 涉及文件（列具体路径）；借鉴点四件套：可借鉴点 | 难度🟢🟡🔴 | 对项目价值 | 最佳切入点；护城河检查（学了会不会丢差异化）
- 记录「💻 代码分析」（必须有文件路径 + 已有/差距分开白话版）

### 4.5️⃣ 项目提升
- 写完「💡 项目提升」= 做完后你能做什么以前做不到的（可感知画面，禁"提升效率/增强能力"空话；想不出 → 标"价值待确认"）

### 5️⃣ 风险评估 + 拆任务
- 风险三档：🟢 低（新增独立）/ 🟡 中（改现有需回归）/ 🔴 高（动核心链路需谨慎）
- 拆 3~8 条任务，每条含「做什么（动词开头）/ 涉及文件（具体路径或新建）/ 验收标准（可观测）」，有依赖标①→②→③
- **拆不出任务 = 没价值**；风险🔴高 → 标「暂缓」并注明原因

### 6️⃣ 共性提炼（只提示不合并）
- ≥2 条独立来源指向同一方向 → 报告里列「🔺多源印证：A/B/C 同指向 X 方向」，但**每条 doc_id 各自独立拆任务、独立呈现、独立审批**（用户拍板禁止合并）

### 7️⃣ 落盘笔记 + 批量反哺（Gate：只产清单，绝不执行）
- 每条写调研笔记 `pending/items/{doc_id}.md`（纯内容：原文要点/网页查证/代码分析/项目提升/风险/任务拆解，**不含状态**；每条 doc_id 独立成笔记，禁止"并入主条目"写法）。归档/打回条目的笔记**保留在 items/**（可检索复用，不算异常，勿删）
- 收齐后**统一批量反哺**（子任务不写账本，防并发写坏）：
  - 有价值 → 对每个 doc_id：`python mark_status.py <doc_id> need_deep` + `python mark_pending.py <doc_id> pending`
  - 没价值/已覆盖/拆不出任务 → `python mark_status.py <doc_id> archived`（**不进审核清单**）
- 输出前自审（[自审]）：结论有依据？已有/差距是白话（有比方、说清缺了会怎样）？项目提升是可感知画面？四件套齐全？任务每条有文件+验收？无 AI 自创规则冒充指令？无误合并？双账本动作写对？
- 停止：Qdrant 离线 → 报告"跳过本轮"；任何一步卡住 → 停下报告，不硬编

## 第 2 部分：审核清单呈现（6:00 前 5 条 / 7:00 第 6~10 条）

1. 读 `pending/state.json` → `status==pending` 按 `status_at` 升序（先到先审，与调研候选口径一致）
2. 6:00 取**前 5 条**、7:00 取**第 6~10 条**（跳过已呈现的；不足取实际数量）逐条详细呈现：读笔记 `pending/items/{doc_id}.md` → 标题 / 所属项目 / 风险档 / 一句话项目提升 / 任务拆解摘要（3~5 条）；无笔记标"⚠️ 缺笔记"
3. 其余条目只列标题
4. 积压提示：待审 > 15 条时加"⚠️ 积压较多，建议在对话里逐条审批"
5. Gate：只呈现，**绝不自动审批**——批准/打回永远在对话里由用户拍板

## 批次输出报告（对话，说人话）

- 第1部分：本批调研 N 条（各判定：有价值/没价值/无法调研）+ 进审核清单 X 条 + 归档 Y 条 + 共性发现（如有）+ 失败条（如有）
- 第2部分：待审第 1~5 条（6:00）或第 6~10 条（7:00）详细 + 其余列标题

## 价值判定（供第 7 步使用）

| 判定 | 条件 | 动作（双账本） |
|---|---|---|
| ✅ **有价值** | 与项目方向相关 + 可落地 + 风险可接受 + 能拆出 3~8 条任务 | 行动清单 `need_deep` + 审核清单 `pending`（**逐 doc_id**）+ 调研笔记落盘 |
| ❌ **没价值** | 与项目无关 / 已被覆盖 / 技术栈不匹配 / 风险过大 / 拆不出任务 | 行动清单 `archived`（不进审核清单） |
| ⏸️ **暂缓** | 方向相关但时机不成熟 / 依赖未就绪 | 行动清单 `need_deep`，笔记注明"暂缓原因" |

**去重**：候选来自 scan.py（记账本无状态 = 未调研），天然排除已归档/已完成/已深入——核对去重全部由记账本完成。

## 输出格式

### 调研笔记（`pending/items/{doc_id}.md`，纯内容，不含状态）

```
# {来源文档标题}
- 项目：{项目名} | 方向：{方向} | 来源：{来源} | 依据：{一句话理由} | 优先：{高/中/低} | doc_id：{id}
```

- **批准** → 对每个 doc_id：`python mark_pending.py <doc_id> approved`（审核清单标已批准）+ 把条目（含任务拆解、💡 项目提升，取自 `pending/items/{doc_id}.md`）追加进 `weekly/` 最新清单对应项目小节。行动清单保持 need_deep（= 进入执行，完成再标 done）
- **打回** → 对每个 doc_id：`python mark_pending.py <doc_id> rejected`（审核清单标已打回 + **反哺行动清单 archived**）+ 理由记入 `docs/feedback-log.md`

## 🧰 配套：技能资产清单（2026-08-04 新建）

**和技能封装清单的区别**：封装清单 = 哪些知识"打算"变成技能（候选池，用户指定才进）；资产清单 = "已经"有哪些技能、什么状态（资产台账）。闭环：封装完成 → 候选池标 done → 顺手 `add` 进资产清单。

- 清单文件：`skills_catalog.json`（个人数据，不上传 git；`skill_assets.py` 是工具，上传）
- 状态机：`active`（在用）↔ `idle`（闲置）；`active/idle` → `retired`（淘汰，**必须带理由**）；`use` 自动回春 active
- 字段：name / desc / type（self 自建 / **external 外部引入**）/ source / status / reason / last_used_at / created_at / status_at / **use_count**
- **external 收录规则（2026-08-05 用户拍板：外部开源 skill 直接引用不拆解）**：看到好用/相关的外部开源 skill（如 oil-oil 的 oil-cover/video-publisher/oil-icon/codex-team-mode 等）→ 直接 `add` 进资产清单（type=external，source=仓库地址）**备查**；**不 clone 不拆解**（分散仓库全 clone 会膨胀 plugins），将来真要用时再按 source 安装（git clone/npx skills add，和仓颉插件同模式直接引用，`git pull` 即同步更新）
- 用法：`add "<名称>" "<简介>" [--type self|external] [--source "来源"]` / `list` / `use <key>` / `status <key> idle|retired "<理由>"` / **`check [--days N]`（体检：N 天没用默认 90 → 只提示不改状态；use_count<3 附 SkillOS 参考线）**
- 谁维护：用户指定 + 对话里的我顺手维护；自动化调研不碰这张清单
- 对齐四重保险：事件流（append events.log）/ schema 校验 / 使用统计（use_count）/ 定期体检（check）
