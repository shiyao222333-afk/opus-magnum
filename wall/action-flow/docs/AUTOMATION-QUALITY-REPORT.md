# 研究报告：为什么自动化 SOP 达不到对话级质量 —— 根因分析与解法

> 日期：2026-08-04 | 触发：用户指出"自动化任务与对话是同一个 AI，SOP 驱动不可能做不到对话级的深入研究"
> 方法：①外部研究（Context Engineering / Agent-ready SOP 最佳实践）②自我记忆分析（用户全局规则 + 项目记忆）③项目管理文件分析（project-management-workflow skill）
> 状态：研究报告（未改任何代码，等用户拍板后落地）

---

## 一、结论先行

**用户判断正确**：自动化任务与对话是同一个 AI 模型，只是驱动方式不同。"做不到"不是模型能力问题，是 **SOP 只写了"步骤"，没写"对话里我是怎么判断的"**——判断标准、用户记忆、反馈回路、思维纪律，全都没编码进去。

一句话根因：
> **对话里的我 = 记忆 + 反馈 + 纪律 + 验证；自动化任务 = 一段 600 字步骤列表。差距不在模型，在"上下文没加载、纠正没记住、判断没写清"。**

---

## 二、对话里我为什么深入？（自我记忆分析）

### 2.1 对话里我自动加载的"上下文"

| 来源 | 内容 | 对"深入"的贡献 |
|---|---|---|
| `~/.workbuddy/MEMORY.md`（290+ 行全局红线） | 不伪造用户指令 / 验收 diff 真实内容 / 找根因不散补 / Gate 确认铁律 | 判断"什么是对的" |
| 项目 `MEMORY.md`（75 行精华） | 环境坑 / 验收流程 / 架构决策 / 各器现状 | 判断"项目能不能用" |
| 当天日志 | 今天做过什么、踩过什么坑 | 避免重复踩坑 |
| `PROJECT_PLAN.md` / `BLUEPRINT.md` | 路线图 / 项目宪法 | 判断"该不该做" |
| `project-management-workflow` skill | Phase 0-5 完整纪律 | 保证"怎么深入"有章法 |

### 2.2 对话里有反馈回路（真正的差距所在）

过去几天用户至少 10+ 次纠正我，每次都成了长期记忆：
- "归档应该有三段的" → 纠正我对归档语义的理解（不是已归档/冷归档/待删除，而是需深入/已完成/已归档）
- "许清楚污染来源" → 纠正我对作者字段污染的误判
- "闪念笔记识别不能靠 source 字段" → 纠正技术判断
- "之前稳定运行过，不是环境问题" → 纠正归因方向，逼出真根因
- "我要的是任务清单，不是调研" → 纠正产出形态

**这些纠正就是外部研究里说的 correction log——别人用 18 个月积累 180+ 条纠正日志，把自动化准确率从 71% 提到 94%。** 我的自动化任务**一条纠正都没存过**，每次跑完就忘。

### 2.3 对话里有验证习惯

对话里我会：实际读代码（app.py/serve.py/search_engine）、进 9 个网页查原文、跑渲染验证、确认"这条能用/不能用"有依据。自动化 prompt 没有强制任何验证动作。

## 三、别人怎么做的（外部研究：Context Engineering）

### 3.1 核心结论：质量差距 = 上下文差距，不是 prompt 差距

搜索到的实践（goaspi / LinkedIn / launchcodex / termdock）一致指向：
> "差异不在更聪明的模型，在更聪明的 context。同一颗引擎，但用了对的燃料。"

### 3.2 Agent-ready SOP 的七要素（我的 SOP 缺了 5 个）

| 要素 | 含义 | 我的 v2.0 SOP |
|---|---|---|
| required_inputs | 明确输入标准 | ⚠️ 部分（有 doc_id 但没校验） |
| tools | 明确用什么工具 | ✅ 有 |
| actions | 明确做什么 | ✅ 有 |
| **decision_rules** | **决策规则（什么情况怎么判断）** | ❌ 没有（"有价值"没定义） |
| **validation** | **产出质量怎么机器可查** | ❌ 没有 |
| **escalation** | **什么时候停止升级给人** | ❌ 没有 |
| **output_schema** | **输出结构严格化** | ⚠️ 部分 |

### 3.3 SOP 失败的 7 个原因（LinkedIn 实证，我中了 6 个）

1. ❌ **太叙述化**：只描述过程，不定义执行逻辑 —— 我的 SOP 是叙述
2. ❌ **隐藏决策标准**：真正的判断在人的脑子里，不在文档里 —— "有价值/没价值"的判断标准没写
3. ⚠️ 缺输入标准：条目来源质量不一
4. ❌ 规则与例子混用：分不清"必须做"与"参考"
5. ⚠️ 缺版本控制
6. ❌ **缺验证**：产出流畅但没有机器可查的质量标准
7. ❌ **缺停止条件**：该升级给人时不升级

### 3.4 Correction Log 是最有效的杠杆（goaspi 实测）

- 18 个月积累 180+ 条纠正日志 → 准确率 71% → 94%
- 机制：每次纠正都记下来 → 下次运行前加载 → 不再犯同样的错
- **我的自动化完全没这个机制，等于每次从零开始、每次都犯同样的错**

### 3.5 上下文不是越多越好（InfoWorld 研究）

- 2~3 个聚焦 skill：性能 +18.6 点
- 4+ 个 skill：塌缩到 +5.9 点
- 全量文档：-2.9 点（反而有害！）

→ **解法不是把 MEMORY.md 全文塞进自动化 prompt，而是提炼"决策规则 + 红线 + 反馈日志"三样东西，控制篇幅。**

### 3.6 其他可借鉴规则

- **硬规则放最前**：中间位置的约束被违反率高 3 倍
- **指令与上下文分离**：instructions（怎么做）vs context（需要知道什么）分开
- **上下文要标"最后验证日期"**：防漂移

## 四、项目管理文件分析（project-management-workflow 为什么在对话里有效）

对照 skill 的 Phase 链 vs 我的自动化 prompt：

| skill 要素 | 对话里 | 自动化 prompt |
|---|---|---|
| Pre-flight（读记忆/蓝图/日志） | ✅ | ❌ 不读任何记忆 |
| Phase 0 意图分类 | ✅ | ❌ 不分类直接跑 |
| Phase 0.5 代码探索（未探索就拆解=违规） | ✅ | ⚠️ 有"看代码"但没有强制纪律 |
| Phase 1.5 方案讨论 Gate（确认后才做） | ✅ | ❌ 无 Gate |
| Phase 3 验证（L1-L4） | ✅ | ❌ 无验证 |
| Phase 5 记忆归档 | ✅ | ❌ 不归档 |

**结论**：project-management-workflow 本身就是"对话级 SOP"——它有效是因为它假设我有完整上下文 + 会遵守纪律。自动化任务直接抄它的骨架（Pre-flight / 分类 / 探索 / Gate / 验证 / 归档），再补上记忆加载和反馈日志，就能达到对话级质量。

## 五、解决方案：SOP v3.0 设计（三层架构）

对齐 Context Engineering 的"基础层 / 任务层 / 反馈层"：

### 第 1 层：基础上下文（每次运行强制加载，控制篇幅）

存 `RESEARCH-GUIDE.md` 顶部"决策规则"区（≈500 字）：
- **用户红线**（提炼自 MEMORY.md）：不伪造用户指令 / 找根因不散补 / 验收 diff 真实内容 / Gate 确认
- **决策规则显式化**："有价值"= 与项目方向相关 + 能拆出 3~8 条可执行任务 + 风险可接受；"没价值"= 已被覆盖 / 技术栈不匹配 / 拆不出任务
- **停止条件**：Qdrant 离线 / 读不到 doc_id / 条目理解不了 → 停止并报告，不硬编

### 第 2 层：任务层（prompt 升级）

保留 6 步，每步补三件套：
- **decision_rules**（这一步怎么判断）
- **validation**（这一步产出怎么验证）
- **escalation**（什么情况停下来问人）

### 第 3 层：反馈层（新建 correction log）

- 新文件：`wall/action-flow/docs/feedback-log.md`
- 用户每次"批准/打回/纠正"的理由 → 记入日志
- 下次自动化运行前先读日志 → 不再犯同样的错

## 六、落地任务清单（等用户拍板）

1. `RESEARCH-GUIDE.md` 升级 v3.0：顶部加"决策规则 + 红线 + 停止条件"；6 步每步加 decision_rules / validation / escalation
2. 新建 `docs/feedback-log.md`：先录入本次 4 条用户纠正（任务清单不是调研 / 自动化不该代替对话 / B 方案 / "不可能做不到"）
3. 自动化任务 prompt 更新：加 Pre-flight（读 MEMORY.md 红线摘要 + feedback-log + 上次 pending 产出）+ 输出前自审 + 停止条件
4. 用首轮 11 条做回归：按 v3.0 重跑巨作 5 条，对比 v2.0 差异
5. 用户批准/打回理由 → 持续记入 feedback-log

---

## 七、一句话总结

> **对话里我能深入，是因为记忆 + 反馈 + 纪律都在；自动化差很远，是因为这三样全没编码进 SOP。解法不是"更好的 prompt"，是"给自动化装上记忆、反馈日志和判断规则"——这正是 Context Engineering 的核心，而 correction log 是其中被验证最有效的杠杆（71%→94%）。**
